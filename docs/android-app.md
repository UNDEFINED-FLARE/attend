# UniAttend Android app

The Android app is a native shell (Capacitor 8) around the deployed UniAttend web app. Every screen, check-in rule
and permission check still runs on the server, so:

- web changes reach phones immediately, with no Play Store update;
- after one signed-in sync it also works **without a connection**: the timetable, dated classes, modules, venues, recent
  attendance and the home screen come from a copy saved on the phone (see [Offline](#offline)), and check-ins made offline
  are queued and sent later, as before;
- it opens with the phone's **fingerprint, face or screen lock** (PIN, pattern or password) when the person turns on the
  app lock, online or not (see [App lock](#app-lock));
- people download it from the website's **Get the app** page, `/app` (see [section 4](#4-put-the-app-on-the-website));
- QR scanning uses the phone camera and check-in uses the phone GPS. Android asks for each permission the first time.

| Item | Where |
|---|---|
| Web address the app opens | `mobile/app.json` → `url` |
| App id (permanent once on Google Play) | `mobile/app.json` → `appId` (`za.uniattend.app`) |
| Native project | `android/` (generated by Capacitor, then customised: permissions, icons, no cloud backup) |
| Offline / start screens | `mobile/www/` (only shown before the first signed-in sync; after it, `/offline` on the site) |
| Website download | `/app` (`src/app/app/`), reading `public/downloads/android.json`; `npm run android:publish` fills it |
| Icons and splash | `node scripts/mobile-assets.mjs` draws them from the UniAttend mark |

## 1. Set the web address

Edit `mobile/app.json` and put your deployed address in `url`, e.g. `https://uniattend-xyz.vercel.app`.
Also add that address to Supabase → Auth → URL configuration if it isn't there yet.

## 2. Build a test APK

**On GitHub (no Android Studio needed):** Actions → *Android app* → *Run workflow* (optionally type the web address).
When it finishes, download **uniattend-debug-apk** from the run's *Artifacts*, unzip it, copy `app-debug.apk` to the phone
and open it (allow "install unknown apps" once).

**On this PC** (needs JDK 21 and the Android SDK, both installed here):

```bash
npm run android:build
```

The APK is written to `android/app/build/outputs/apk/debug/app-debug.apk`. To try the app against a local dev server in the
emulator, use `node scripts/mobile.mjs build --url http://10.0.2.2:3001` (10.0.2.2 is this PC as seen from the emulator).

## 3. Publish on Google Play

1. Create an upload key once and keep it safe (losing it means you can't update the app):
   ```bash
   keytool -genkeypair -v -keystore uniattend-release.jks -alias uniattend -keyalg RSA -keysize 2048 -validity 10000
   ```
2. Create `android/keystore.properties` (never committed; `.gitignore` covers it):
   ```
   storeFile=../../uniattend-release.jks
   storePassword=…
   keyAlias=uniattend
   keyPassword=…
   ```
3. Raise `versionCode` (and `versionName`) in `android/app/build.gradle` for every upload.
4. Build the bundle and upload `android/app/build/outputs/bundle/release/app-release.aab` in the Play Console:
   ```bash
   npm run android:release
   ```

Play Console needs a privacy policy URL (`/privacy` on your site) and the data-safety form. The app collects
location at check-in (used once, only the distance is stored), the camera for QR scanning (not stored), and a device hash.
Where an institution turns Bluetooth on, it also uses "Nearby devices" to hear the class signal at check-in (only a summary is
stored) and, on a lecturer's phone, to broadcast it.

## 4. Put the app on the website

The **Get the app** page (`/app`, linked from the home page header and footer and from `/login`) offers the APK with its
version, size, SHA-256 checksum and install steps, plus the iPhone and browser options. It reads
`public/downloads/android.json`; until that exists it says the download isn't available yet.

```bash
npm run android:publish
```

This builds the APK and copies it to `public/downloads/uniattend-<version>-<code>.apk` with its manifest (only the newest
APK is kept there). The website serves it as a static file (`application/vnd.android.package-archive`, as an attachment),
so it goes live with the next deploy once those two files are committed.

- **Signed release (what people should get):** needs `android/keystore.properties` and the keystore from section 3. The
  script then builds `assembleRelease`. Keep the key safe: phones only accept an update signed with the same key, and
  never commit the keystore or `keystore.properties`.
- **No key yet:** the script publishes the debug build and the page labels it a *test build*. A later release build can't
  install over a test build (different key): people uninstall the test build first.
- Raise `versionCode` and `versionName` in `android/app/build.gradle` before each new release.
- `--skip-build` publishes the APK already built; `--url https://…` builds for another web address;
  `--host https://…/uniattend.apk` makes the page link to the APK hosted elsewhere (a GitHub release or a storage
  bucket). The file is still written to `public/downloads/` so you can upload it, and the checksum matches it.
- Every deploy carries the APK (about 5–10 MB). If that becomes a burden, host it with `--host` and commit only
  `android.json`.

**iPhone** is not covered by a website download: Apple only installs apps from the App Store (or TestFlight for testing).
The page tells iPhone users to add the website to the Home Screen from Safari, which gives them the same offline copy and
an app lock with Face ID, Touch ID or their passcode.

**The website stays an installable web app (PWA)** for everyone else, through `public/manifest.webmanifest` and the
service worker `public/sw.js`.

## Offline

After a person signs in once with signal, the app keeps a copy of what they need on the phone and refreshes it whenever
it is online (on opening, on coming back online and on returning to the app, at most every ten minutes):

| What | Student | Lecturer |
|---|---|---|
| Weekly timetable | their modules | the classes they teach |
| Dated classes, next seven days (cancellations and changes marked) | ✓ | ✓ |
| Modules | with their own attendance and the minimum | with enrolled students |
| Venues | name and location; "Open in maps" opens the phone's map app | same |
| Recent history | last 60 attendance records | attendance sessions, last two weeks and ahead |
| Home | now / next class, today, overall attendance, check-in | now / next class, today |

How it works:

- `GET /api/offline?role=student|lecturer` (`src/app/api/offline/route.ts`, built by `src/lib/offline-snapshot.ts`)
  returns the signed-in person's copy. Every query runs as that person, so RLS decides what goes in, as for the pages.
  It is sent `Cache-Control: private, no-store`.
- `<OfflineData>` (in the signed-in shell) stores it in `localStorage` under `ua_offline_v1:<user id>`
  (`src/lib/offline-data.ts`) and asks the service worker to keep the offline screen and, for students, the check-in page.
- Without signal, the service worker sends the main screens (`/`, `/dashboard`, home, timetable, modules, map, history)
  to **`/offline`**, a page with no personal data in it that draws those screens from the saved copy and shows
  "last updated …". Other signed-in pages (check-in, notifications, settings) open as last seen with signal. When the
  signal returns, `/offline` goes back to the page that couldn't load.
- **Check-ins offline** are unchanged: the check-in page (kept by the service worker) queues them, they are sent later
  with `check_in_offline`, always land as `pending_verification`, and the QR is checked against its own 20-second window.
- **Shared phones:** the copy is keyed by user; any other person's copy is deleted when someone syncs; the service worker
  drops its kept pages when a different person signs in; and every sign-in page (where signing out lands) deletes all
  copies and kept pages. The offline queue was already per person.
- The campus map's tiles come from the internet, so the map itself needs signal; venue names and locations don't.

This is the same in the Android app and in the browser: the app's screens come from the website, and Android's WebView
runs the site's service worker. `mobile/www/offline.html` only appears when the phone has never synced (no service
worker yet).

## App lock

*Security → App lock* (`src/app/settings/app-lock-settings.tsx`, `src/lib/app-lock.ts`):

- **Android app:** the phone's BiometricPrompt through `@capgo/capacitor-native-biometric`, allowing fingerprint, face
  and the **device credential** (PIN, pattern or password), so it also works on a phone with no biometrics enrolled.
  Android shows no Cancel button when the screen lock is allowed; back or a swipe cancels.
- **Browsers and the iPhone home-screen app:** a platform passkey made only for the lock (Windows Hello, Touch ID,
  Face ID, Android fingerprint or the device PIN).
- Both run entirely on the device, so the lock also works offline, including on `/offline`.
- **No biometric data ever leaves the phone:** the operating system checks the finger, face or PIN and only answers
  "verified" or not. UniAttend keeps the setting (and for browsers the passkey's id) on the device and nothing on the server.
- "Use my password instead" signs out (and so wipes the offline copy); it needs signal.

## Notes

- **Start page:** the app opens the site's front page, `/`. For someone signed in, the middleware sends `/` straight to
  `/dashboard` (their own home), so reopening the app never shows the public page with its "Sign in" button. `/?home=1`
  still shows the public page.
- **The app shows whatever the website runs:** offline mode, `/offline` and the new service worker reach phones only once
  the website is deployed. A new APK is only needed for native changes.
- **Bluetooth presence** (update 0037) runs only in this app, through its own plugin `UniAttendBlePlugin`: the lecturer's
  phone broadcasts a rotating class signal and students' phones listen for it at check-in. See [bluetooth.md](bluetooth.md).
  A new app build is needed for it; older builds simply don't send Bluetooth evidence.
- **Email confirmation links** open in the phone's browser. After confirming, sign in in the app.
- The app keeps sign-in and the device id on the phone only: Android backup and device transfer are switched off.
